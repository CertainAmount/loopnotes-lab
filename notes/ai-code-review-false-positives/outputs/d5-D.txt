- `get_rate_counted` does a non-atomic read-modify-write on `_hits` (`get` then assign). Concurrent calls for the same currency can lose increments, so partners are under-billed. Guard the update with a lock.
- `billing_report` iterates `_hits.items()` with no synchronization. If another thread adds a new currency key during iteration, it can raise `RuntimeError: dictionary changed size during iteration`, which would fail the monthly invoice job.
- `_hits` is never reset after `billing_report` runs, so counts carry over from month to month and partners get billed again for earlier hits. If a reset is added, the snapshot and the reset must happen atomically under the same lock, or hits that land between them are lost.
- Billable usage is stored only in process memory. A restart or crash wipes the counts, and with multiple workers or processes each one has its own `_hits`, so the invoice job sees only a fraction of real usage. Billing data needs durable, shared storage.
