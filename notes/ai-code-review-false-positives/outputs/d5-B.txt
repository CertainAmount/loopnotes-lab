- `get_rate_counted` increments `_hits` with an unsynchronized read-modify-write (`n = _hits.get(...)`, then `_hits[cur] = n + 1`). `quote()` runs it concurrently on a 16-worker pool, so increments get lost and partners are under-billed. Guard the increment with a `threading.Lock` (or use a locked `collections.Counter`).
- `billing_report` iterates `_hits` while worker threads may be inserting new keys. This can raise `RuntimeError: dictionary changed size during iteration` during `close_month()`. Snapshot under the same lock used for increments.
- `billing_report` never resets `_hits`, so counts keep accumulating across months. Each monthly invoice re-bills all prior months' hits. Atomically snapshot and clear (or key by period) when closing the month.
- Billing counts live only in process memory. A restart or deploy before the monthly job silently drops billable usage, and running multiple processes or replicas splits counts so one process reports only part of it. Billing data needs durable, shared storage.
- `get_rate` has a check-then-set race. Concurrent first requests for the same currency each call `fetch_rate`, causing redundant upstream fetches. Lock it or use per-key once-initialization.
- The comment says "each hit is billed", but `get_rate_counted` also counts cache misses (the first call that triggers `fetch_rate`). Confirm whether partners should be billed per request or per cache hit, and name or count accordingly.
