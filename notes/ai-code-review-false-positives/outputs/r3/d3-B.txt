- `export_month` leaks the SQLite connection on the `if not rows: return 0` path because `conn.close()` is never reached. The hourly job runs inside one long-lived worker, so every empty-month run (common early in a month) leaves a connection and file handle open. Use `try/finally` or `contextlib.closing(sqlite3.connect(db_path))`. Note that `with sqlite3.connect(...)` alone only manages transactions and does not close the connection.
- The connection is also leaked if `conn.execute`, `fetchall`, or `write_rows` raises (for example a missing table, locked DB, or unwritable `/var/exports`). Close it in a `finally` block, not only on the happy path.
- `conn.close()` runs after `write_rows`, so the DB connection stays open for the whole file write. Fetch the rows, close the connection, then write the CSV.
- When no rows are found, nothing is written. A previously exported `payments-{month}.csv` from an earlier hourly run stays on disk, so if rows were deleted or corrected, consumers keep reading stale data. Either write an empty file (or header) or remove the existing file.
- The hourly run overwrites `out_path` in place, so a reader that opens the file mid-write sees a truncated CSV. Write to a temp file in the same directory and `os.replace` it onto `out_path`.
- The query has no `ORDER BY`, so row order in the CSV can change between hourly runs even when the data hasn't. Add `ORDER BY id` (or `created_at`) for deterministic output.
- `fetchall()` loads the whole month into memory. Consider passing the cursor straight to `write_rows`, which already iterates, but count the rows separately for the return value.
