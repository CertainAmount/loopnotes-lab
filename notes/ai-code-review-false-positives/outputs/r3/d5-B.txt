- `get_rate_counted`: the `_hits.get(cur, 0)` read and the `_hits[cur] = n + 1` write are not atomic. `quote()` calls this from a 16-worker `ThreadPoolExecutor`, so concurrent requests for the same currency lose increments and partners are under-billed. Guard the update with a `threading.Lock`, or use a lock-protected `collections.Counter`.
- `billing_report`: it iterates `_hits` without the lock while worker threads may be inserting new keys. This can raise `RuntimeError: dictionary changed size during iteration`, and it can return a snapshot that mixes counts from different moments. Take the same lock and copy the dict under it.
- `billing_report`: counts are never reset. Each monthly `close_month()` returns cumulative totals since process start, so partners are re-billed for every previous month's hits. Snapshot and clear under the lock, or key counts by billing period.
- `_hits` is held only in process memory. A restart, deploy or crash before the month closes silently drops billable usage. If the service runs as several processes or hosts, each one reports only its own share. Billing data should go to durable shared storage such as a DB or Redis `INCR`.
- `get_rate` (existing, but now on a concurrent billing path): the `if cur not in _rates` check followed by the fetch-and-assign is a check-then-act race. Several threads can call `fetch_rate` for the same currency at the same time, which causes redundant upstream calls. Use a lock or a per-key once-guard if `fetch_rate` is costly or rate-limited.
- `billing_report` comment / naming: the comment says "each hit is billed", but `_hits` counts every call, including cache misses that triggered `fetch_rate`. Confirm that billing should be per request and not per cache hit, and rename to `_calls` or `_requests` if per request is what's intended.
