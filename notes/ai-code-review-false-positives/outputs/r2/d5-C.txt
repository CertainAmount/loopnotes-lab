- `get_rate_counted` does a non-atomic read-modify-write on `_hits` (`get` then assign); concurrent calls for the same currency can lose increments, so partners are under-billed. Guard the counter with a lock or use an atomic counter.
- `billing_report()` iterates `_hits.items()` while other threads may insert new currencies, which can raise `RuntimeError: dictionary changed size during iteration` and crash the monthly invoice job. Snapshot under a lock (or `dict(_hits)` while holding it) before iterating.
- `get_rate` has a check-then-act race on `_rates`; concurrent cache misses for the same currency each call `fetch_rate`, causing duplicate upstream fetches. Since `get_rate_counted` now counts calls rather than fetches, this also makes "hits" ambiguous.
- Billing data lives only in process memory: a restart, crash, or deploy silently zeroes `_hits`, and in a multi-process or multi-worker deployment each process has its own counter. Either way the invoice job sees incomplete counts. Billable usage needs durable, shared storage.
- `billing_report()` never resets or windows `_hits`, so counts keep accumulating across months. Partners would be re-billed for prior periods unless reset elsewhere, and resetting separately from reading would race with increments (read-and-reset must be atomic).
- If `fetch_rate` raises, nothing is cached or counted, which is fine. But `_hits` is keyed by caller-supplied `cur` with no validation, so arbitrary or garbage currency strings grow `_hits` (and `_rates`) without bound and show up as billable line items.
- `_rates` entries never expire, so stale exchange rates are served indefinitely. That is a data-integrity problem for pricing and is now directly tied to billed usage.
