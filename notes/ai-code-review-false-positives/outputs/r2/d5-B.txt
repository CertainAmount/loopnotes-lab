- `pricing/cache.py:get_rate_counted`: the `_hits.get` then `_hits[cur] = n + 1` sequence is a non-atomic read-modify-write. `quote()` runs it concurrently on a 16-worker `ThreadPoolExecutor`, so increments get lost and partners are under-billed. Guard it with a `threading.Lock`.
- `pricing/cache.py:billing_report`: the dict comprehension iterates `_hits.items()` while worker threads may insert a new currency key. That can raise `RuntimeError: dictionary changed size during iteration` during the invoice job, and even without the error the snapshot is inconsistent. Take the snapshot under the same lock.
- `pricing/cache.py:billing_report`: `_hits` is never reset after the monthly report. Each `close_month()` returns cumulative counts since process start, so earlier months get billed again. Reset atomically under the lock when the report is taken, or key the counts by billing period.
- `pricing/cache.py`: billing counts live only in process memory. A restart or deploy loses the month's billable usage. With several server processes or workers, each one has its own `_hits`, so `close_month()` sees only one process's share. Billing data needs durable, shared storage.
- `pricing/cache.py:get_rate_counted`: the counter is called `_hits` and the comment says "each hit is billed", but it counts every call, including the first cache miss that triggers `fetch_rate`. Either rename it, for example `_calls`, or count only real cache hits, whichever matches the billing contract.
- `pricing/cache.py:get_rate`: this check-then-set existed before, but it is now reached concurrently through `get_rate_counted`. Several threads can call `fetch_rate` for the same currency at once, which makes duplicate upstream calls that may themselves cost money. Consider locking it or using per-key single-flight.
