- `export_month` (reports/export.py:19-20): when there are no rows, the function returns before `conn.close()`, so the SQLite connection leaks. The job runs every hour for the current month inside one long-lived worker, and early in a month the query will often be empty. Each of those runs leaks another connection and file handle until the worker runs out of descriptors or holds locks on `payments.db`. Close the connection before returning, ideally with `try/finally` or `contextlib.closing(sqlite3.connect(db_path))`.
- `export_month` (reports/export.py:14-23): if `conn.execute`, `fetchall`, or `write_rows` raises (for example, the database is locked or `/var/exports` is not writable), `conn.close()` never runs and the connection leaks in the long-lived worker. Wrapping the body in `closing(...)` or `try/finally` fixes this and the early-return leak together. Note that `with sqlite3.connect(...)` alone only manages transactions and does not close the connection.
- `export_month` (reports/export.py:19-20): when there are no rows, nothing is written to `out_path`. Any CSV already at `payments-{month}.csv` stays in place even though the data now has no rows, and consumers can't tell "no payments" from "export never ran". Consider always writing the (empty) file.
- `export_month` (reports/export.py:21): the CSV is still being written while the connection is open. Since the rows are already fetched, close the connection right after `fetchall()` so it isn't held during file I/O.
