- `export_month` leaks the SQLite connection on the `if not rows: return 0` path because `conn.close()` is never reached. The job runs hourly in one long-lived worker, so every empty month leaks a file handle and connection. Wrap the body in `try/finally` or `contextlib.closing(sqlite3.connect(db_path))`. A bare `with sqlite3.connect(...)` only manages the transaction and does not close the connection.
- If the query, `fetchall()` or `write_rows` raises, the connection is also never closed. That is the same leak on the error path, and `try/finally` fixes it too.
- The connection stays open for the whole CSV write. Close it, or release it via the `finally`, right after `fetchall()` so the DB handle isn't held during file I/O.
- `write_rows` overwrites `/var/exports/payments-{month}.csv` in place every hour. A consumer reading during the write sees a truncated or partial file, and a crash mid-write leaves a corrupt export. Write to a temp file in the same directory and `os.replace` it into place.
- When the month has no rows, the function returns 0 without touching `out_path`. Any CSV left from an earlier run stays in place, so the file and the return value disagree. Decide explicitly whether to write an empty (header-only) file or remove the old one.
- The CSV has no header row (`id, amount, created_at`), so consumers have to know the column order implicitly. Consider writing `[d[0] for d in cur.description]` first.
