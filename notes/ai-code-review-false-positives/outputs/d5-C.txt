- `get_rate_counted`: the read-modify-write on `_hits[cur]` (`n = _hits.get(...)` then `_hits[cur] = n + 1`) is not atomic; concurrent callers can lose increments, under-counting billable hits that feed invoices — guard with a lock or use an atomic counter.
- `get_rate`: check-then-set on `_rates` is racy; concurrent misses for the same currency will each call `fetch_rate`, causing duplicate upstream fetches and possibly different rates returned to different callers.
- `billing_report`: iterating `_hits.items()` while other threads mutate `_hits` can raise `RuntimeError: dictionary changed size during iteration`, failing the monthly invoice job — snapshot under a lock.
- `billing_report`: counts are never reset or partitioned by billing period, so each monthly report includes all hits since process start, double-billing partners on every invoice after the first.
- `_hits` is in-process memory only: counts are lost on restart/deploy and are not aggregated across multiple workers/processes, so billing data is silently incomplete — billable usage should be persisted durably.
- `get_rate_counted`: if `get_rate` raises (e.g. `fetch_rate` fails), the hit is not counted, but if counting is meant to bill only successful lookups this is fine — however there is no handling for `fetch_rate` errors in `get_rate`, so a transient failure propagates and nothing is cached or retried.
- `_rates` cache has no TTL or invalidation, so stale exchange rates are served indefinitely; `_hits` and `_rates` are also unbounded and keyed by caller-supplied `cur`, allowing memory growth (and spurious billing entries) from arbitrary/invalid currency codes if input is not validated.
