- `get_rate_counted` increments `_hits[cur]` with an unsynchronized read-modify-write (`get`, then assign). Concurrent callers can lose increments, so partners are under-billed. Guard the update with a lock or use an atomic counter.
- `billing_report` iterates `_hits.items()` without a lock. A concurrent `get_rate_counted` call that adds a new currency key can raise `RuntimeError: dictionary changed size during iteration` and fail the invoice job.
- The billing counts live only in a module-level dict in process memory. They are lost on restart or crash, and each worker process keeps its own copy. The monthly invoice job, which likely runs in a separate process, will see empty or partial counts. Billable hits need durable, shared storage.
- `billing_report` never resets `_hits`, and nothing scopes the counts to a billing period. Each monthly report includes all hits since the process started, so partners are double-billed for earlier months. Snapshot and reset atomically, or record timestamps per period.
- `get_rate` (now on the billed hot path) has a check-then-set race on `_rates`. Concurrent cache misses for the same currency each call `fetch_rate`, causing duplicate upstream fetches.
